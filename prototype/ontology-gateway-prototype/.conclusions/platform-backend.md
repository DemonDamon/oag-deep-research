# 平台后端模块摘要

## 核心结论

后端采用模块化全栈服务形态，但领域边界已经按未来事件驱动拆分设计。`platformRouter` 是前端与终端接入层的统一契约；`demoData` 提供演示读模型；`platformDb` 负责少量真实写路径。该结构适合先验证对象、证据、决策与 Action 闭环，再逐步把高负载或高风险模块拆为独立服务。

| 模块 | 当前职责 | 生产演进 |
|---|---|---|
| Ontology / Objects | 对象类型、对象、关系、证据和版本查询 | Schema Registry、图/搜索混合读模型 |
| Identity | 异构系统 ID 到统一对象 ID 的映射 | 独立解析服务、冲突队列、人工复核 |
| Connector / Capability | 系统状态与 Query、Function、Proposal、Action、Event 清单 | 独立 Connector Runtime 与凭据托管 |
| OAG / Decision | 对象约束解释、规则计算、方案模拟和影响检查 | 可验证规则服务、检索编排、离线评测 |
| Action / Governance | 提案、幂等、审批、回滚计划和审计 | Action Orchestrator、队列化执行器、补偿状态机 |
| Gateway / Access | AgenticX、Near 接入清单与四角色权限矩阵 | 身份委托、对象级授权、限流与协议适配 |

## 写路径约束

公开接口只能生成非持久化预览。真实提案提交要求认证用户，并以统一对象 ID、能力键、对象期望版本和方案 ID 生成幂等键。提案与创建审计事件位于同一数据库事务中。审批接口要求 `supervisor` 或 `developer_governance` 企业角色，并同步更新提案、审批记录和审计事件。

> 当前原型尚未提供直接执行 Action 的服务端过程。网关清单中的 `action.execute` 是目标契约，不代表浏览器可以绕过审批调用源系统。

## 一致性策略

单库范围采用事务保证提案、审批和审计的一致性；跨 CRM、ERP、MES 的执行不承诺分布式事务，而采用“提案—审批—执行—补偿”状态机。所有执行器必须支持幂等键、期望版本、超时、重试上限和补偿记录。

## 验证状态

Vitest 已覆盖运营概览、OAG 工具轨迹、非持久化提案预览、认证提案提交与审批契约。后续应增加数据库集成测试、并发幂等测试、角色拒绝路径、失败补偿和审计不可变性测试。
